## Naming

Follow the language's standard naming conventions, and the surrounding code where they differ. A name
says what a thing is or does; no abbreviations beyond well-known ones (`id`, `url`, `http`).

## Architecture

- Dependencies point one way: core logic doesn't depend on I/O, UI or frameworks; those call into it.
- One responsibility per module. Side effects (files, network, clock, randomness) stay at the edges.

## Patterns

| Use | Instead of | Why |
| --- | --- | --- |
| The simplest thing that works now | Abstractions for imagined future needs | Less code to read and change |
| Small functions with one job | Long functions with flags that switch behaviour | Easier to name, test and change |
| Explicit inputs: parameters, an injected clock or I/O | Hidden globals and singletons | Testable and predictable |
| Errors returned or thrown to the caller | Swallowing errors, or logging and carrying on | Failures stay visible |

## Errors and logging

- Errors: fail at the point of failure, with enough context to act on; never swallow one silently.
- Logging: through one logger, with levels; never log secrets or personal data.

## Git

- Branch: `type/short-name` · Commit: [Conventional Commits](https://www.conventionalcommits.org/),
  `type(scope): imperative summary`, with types `feat`, `fix`, `docs`, `test`, `refactor`, `build`, `chore`.
- One logical change per commit.
- With work repositories: commit in each repository separately, and update a submodule pointer only after
  the child's change is merged.
