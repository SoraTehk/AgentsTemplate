# 2. Instructions

## Shell commands

Every command in this file is Bash, run in the `Bash` tool from this repository's root, as pasted. Never change
directory: a tool that needs a directory gets it as an argument (e.g. `git -C <dir>`, `cmake -S <dir> -B <dir>`,
`npm --prefix <dir>`). From a parent session, put this repository's path in front of every path in the command.

A command too long for the table is a block below it. Each block stands alone, because an agent's shell keeps no
variables between calls; change only lines marked `# edit`. "Passes when" says what success prints: anything else
is a failure, to report rather than work around. A job marked *not set up yet* counts as missing, so AGENTS.md
rule 2 applies the first time it's needed.

### Branch files

```bash
base=$(git merge-base HEAD origin/main)  # edit: origin/<default branch>
git diff --name-only --diff-filter=d "$base"; git ls-files --others --exclude-standard
```

A `fatal:` line means the `# edit` line names a branch this clone doesn't have.

## Tools by action

## Playbooks

### Set up from a fresh clone

1. Install the prerequisites in [1.PROJECT](1.PROJECT.md#prerequisites).
2. Setup steps: *not set up yet*. With work repositories, include how to fetch them
   (e.g. `git clone --recurse-submodules`).
3. Check it worked: the Build and Test commands above both pass.

Known traps: none recorded yet.

### Answer a question or investigate

1. Check the docs index in AGENTS.md first, then the code. Read only; change nothing.
2. Cite `path:line` for every claim about the code.

### Fix a bug

1. Reproduce it as a failing test (AGENTS.md rule 3), unless [4.TEST](4.TEST.md) exempts it.
2. Fix the cause, not the symptom, until that test passes. Then finish the task as below.

### Add or change a feature

1. Read `docs/<Feature>/README.md`, then each doc its "Docs" table says to read for your task.
2. Write the failing tests for the new behaviour, unless [4.TEST](4.TEST.md) exempts it; then implement.
3. Finish the task as below.

A new feature, and a numbered doc for an existing one, start from [the feature template](_FEATURE_TEMPLATE/README.md).
The block never overwrites a file that exists, and passes when it prints one `made` or `kept` line per file:

```bash
feature='NEW_FEATURE'  # edit: its folder name under docs/
docs=''  # edit: the numbered docs it needs now, e.g. '3.CONVENTIONS 5.DECISIONS'
from=docs/_FEATURE_TEMPLATE
mkdir -p "docs/$feature" .claude/rules
fill() { if [ ! -e "$1" ]; then echo "no template $1"; elif [ -e "$2" ]; then echo "kept $2"; else sed "s|{{FEATURE_NAME}}|$feature|g" "$1" > "$2" && echo "made $2"; fi; }
fill "$from/README.md" "docs/$feature/README.md"
fill "$from/rule.md" ".claude/rules/$feature.md"
for d in $docs; do fill "$from/$d.md" "docs/$feature/$d.md"; done
```

For a new feature, then add its row to AGENTS.md "Feature docs", point the README's **Code** and **Tests** and the
rule's `paths` at its folders, and fill what you know. For each numbered doc, add its row to the README's "Docs" table.

A feature gets a numbered doc only once it has something of its own for it: facts, commands, playbooks, rules, test
layout, decisions or deferred work that the root doc with the same number doesn't hold. Features don't nest
([5.DECISIONS](5.DECISIONS.md) D-002).

### Rename or restructure

1. Check [6.TODOS](6.TODOS.md) and [5.DECISIONS](5.DECISIONS.md) for an existing plan, or a reason not to.
2. A name that stored data holds by its text (serialized files or saved assets, database columns, config keys, a
   public API or message format) is not a plain rename: changing it only in the code drops or breaks that data. It
   needs a migration playbook here; with none, AGENTS.md rule 2 applies.
3. Find every use with the `LSP` tool's references and change each one; move files with `git mv`. The
   existing tests must pass unchanged.
4. Delete the finished TODO, then finish the task as below.

### Sync the docs with the code

Usually run in a fresh session. The user gives a git range; if they don't, the default is the commits since docs/
last changed.

1. List the changes, then read the diffs that matter:

   ```bash
   range="$(git log -1 --format=%h -- docs AGENTS.md)..HEAD"  # edit: the user's range, if they gave one
   git log --oneline "$range"; git diff --stat "$range"
   ```

2. Route each change: commands and tools → 2.INSTRUCTIONS (ask first, per AGENTS.md rule 2); purpose,
   milestones, prerequisites, layout → 1.PROJECT; style, architecture, contracts → 3.CONVENTIONS; test
   layout → 4.TEST; a choice between real alternatives → 5.DECISIONS; deferred work → add to 6.TODOS, and
   delete finished ones. A change that belongs to one feature goes in that feature's doc with the same number,
   created if it has none yet, and its behaviour and contract in `docs/<Feature>/README.md`.
3. Make the smallest edit that makes each doc true. Describe the present, not history. Write only facts
   you verified. Skip anything the code, a linter or the types already say. Put a fact in the repository
   it is about, and link to it from elsewhere instead of copying it.
4. Check:
   - every doc directly in `docs/` except `_`-prefixed ones is linked from AGENTS.md, every other file in a
     `docs/<Feature>/` folder from that feature's README, and every link resolves;
   - each feature's "Docs" table lists exactly the numbered docs in its folder, and each of those holds something
     its root doc doesn't;
   - no `{{` placeholders remain outside `docs/_FEATURE_TEMPLATE/` and the feature block above;
   - CLAUDE.md is still `@AGENTS.md`; each `.claude/rules/*.md` `paths` still matches real files and its feature
     README's **Code**; `.claude/agents/SUBAGENTS.md` frontmatter is valid YAML with a `name` and `description`.
5. Report the files you changed, one line each, and anything you couldn't verify.

### Change a contract with another repository

1. Update the spec in `docs/<Feature>/` and its row in [3.CONVENTIONS](3.CONVENTIONS.md#contracts-with-other-repositories).
2. Change the producer, then every consumer. With work repositories, hand each side to its agent.
   Run each one's tests.
3. Commit in each repository separately.

### Finish any task

1. Run the build, the full test suite and lint (Shell commands above). All must pass.
2. Report what you ran and the result. Note anything left undone as a candidate for 6.TODOS.
